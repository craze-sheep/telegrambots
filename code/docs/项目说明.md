# Telegram AI Team Bot-to-Bot 版本

版本：v1.0.0-beta
最后更新：2026-05-30

这个目录是当前保留的中心化 bot-to-bot 项目。

目标：去掉固定工作流，让 Telegram 群聊本身承担“经理 @ 调度、角色 @ 回报”的可见协作体验。

```text
用户 -> Supervisor 经理 bot
Supervisor -> @Planner / @Researcher / @Developer / @Tester
Worker bot -> @Supervisor 回报
Supervisor -> 继续 @下一个角色，或汇总 DONE
```

## 重要区别

这个版本不使用原项目的固定状态机，也不内置“必须按某个顺序走”的流程：

```text
Planner -> Researcher -> Developer -> Tester -> Supervisor  # 已移除
```

而是让 Supervisor 在群里自己判断下一步要 `@` 哪个角色。其他四个 bot 只在被 @ 时回复，并且回复时 @Supervisor。

这个版本以 Supervisor 为中心，不允许 worker 互相调度，也不设置固定最大轮数。是否继续、换人、结束，都由 Supervisor 决定。

通信拓扑固定为星型：

```text
你 <-> Supervisor
Supervisor <-> Planner
Supervisor <-> Researcher
Supervisor <-> Developer
Supervisor <-> Tester
```

worker 之间即使互相 @，接收方也会忽略；worker 的模型提示词也禁止 @ 或安排其他 worker。

worker 只响应 Supervisor 发出的派单消息，且消息开头必须是 `[任务ID][Supervisor][ASSIGN]`。Supervisor 的 `[DONE]` 总结里可以正常写真实 `@username`，worker 会把这些 `@` 当成展示文本，不会再次触发执行。

代码层面还有一层出站门禁：worker 只能向群里发送 `[任务ID][角色][REPORT]` 回报消息；任何 worker 试图发送 `[WORKING]`、`[STATUS]`、`[ASSIGN]`、`[DONE]` 或其他普通群消息，服务会先拦截并把规则错误回灌给该 worker，让它重新输出一次。第二次仍不合规时，Supervisor 发送 `[ERROR]`，不会把本地 fallback 伪装成成功 REPORT。worker 回报里除 `@Supervisor` 外的所有 `@username` 也会被去掉。

## 工作目录产物

每个任务都会创建一个产物目录：

```text
artifacts/
  tasks/
    B2B-YYYYMMDD-HHMMSS/
      README.md
      supervisor/
        001-...-assign-planner.md
        002-...-done.md
      planner/
        003-...-report.md
      researcher/
      developer/
      tester/
      files/
        relative/path/from/model.ext
  tmux-jobs/
    role-...prompt.txt
  hermes-role-prompts/
    supervisor.md
```

规则：

- Supervisor 的每次派单和最终汇总都会保存为 Markdown；
- Planner、Researcher、Developer、Tester 的每次回报都会保存为 Markdown；
- 每份 Markdown 会记录任务 ID、角色、skills、MCP、交接摘要、群聊正文；
- 如果模型在回复中使用 `FILE: relative/path.ext` 加代码块，且用户指定了真实工作目录，服务会把文件写入该绝对工作目录；否则写入 `artifacts/tasks/<任务ID>/files/` 草稿区；
- 文件路径只允许相对路径，包含绝对路径、`..` 或 Windows 盘符的产物会被忽略；
- 这些文件是 bot 的工作产物和代码草稿，不代表已经被自动合并到项目源码。

清理旧任务产物：

```bash
python3 scripts/cleanup_artifacts.py --days 30 --dry-run
python3 scripts/cleanup_artifacts.py --days 30
```

默认只清理 `artifacts/tasks/B2B-*` 任务目录，也兼容清理旧版遗留的 `artifacts/B2B-*`，不会删除 `artifacts/hermes-role-prompts/`。如需同时清理旧 tmux job 调试文件：

```bash
python3 scripts/cleanup_artifacts.py --days 30 --include-tmux-jobs
```

## 后续混合 Agent 设计

当前版本所有角色默认都走 `tmux_hermes`。如果以后不想所有 bot 都使用同一个 Agent 后端，可以把 `TmuxHermesClient` 抽象成统一的 `AgentRunner`，让每个角色单独选择后端。

目标结构：

```text
Telegram bot
  -> BotToBotTeam
  -> AgentRunner
      -> TmuxHermesRunner
      -> ClaudeCodeRunner
      -> DirectLLMRunner
```

建议的角色分配：

```text
Supervisor: Hermes
Planner: Hermes
Researcher: Hermes
Developer: Claude Code
Tester: Claude Code
```

原因：

- Hermes 更适合群聊调度、角色协作、skills/MCP 组合和长期上下文；
- Claude Code 更适合真实代码阅读、修改、审查和测试；
- Direct LLM 只适合作为 fallback，不建议作为主要执行后端。

未来可以增加类似下面的配置：

```env
SUPERVISOR_AGENT_BACKEND=tmux_hermes
PLANNER_AGENT_BACKEND=tmux_hermes
RESEARCHER_AGENT_BACKEND=tmux_hermes
DEVELOPER_AGENT_BACKEND=claude_code
TESTER_AGENT_BACKEND=claude_code
```

实现步骤：

1. 定义统一接口：`complete(role, system_prompt, user_prompt) -> str`；
2. 把当前 `TmuxHermesClient` 改名为 `TmuxHermesRunner`；
3. 新增 `ClaudeCodeRunner`，用 `claude -p` 或 Claude Code tmux 会话执行；
4. 在 `ROLES` 或 `.env` 中为每个角色指定 backend；
5. 保持 Telegram 层、任务 ID、artifact 落盘和 worker 隔离规则不变。

安全边界：

- Claude Code 后端如果允许真实改文件，不应由 Telegram prompt 无审批触发危险操作；
- 更稳的做法是先让 Claude Code 产出 patch、计划或 `artifacts/tasks/<任务ID>/files/` 草稿，再由人工确认合并；
- worker 之间仍然不能互相通信，混合后端只改变“角色背后的执行器”，不改变星型通信拓扑。

## Hermes Tmux 会话

默认会话名：

```text
telegrambots-supervisor
telegrambots-planner
telegrambots-researcher
telegrambots-developer
telegrambots-tester
```

手动启动或重启：

```bash
python3 scripts/start_hermes_tmux_agents.py
python3 scripts/start_hermes_tmux_agents.py --restart
```

查看某个角色：

```bash
tmux attach -t telegrambots-developer
```

停止全部角色：

```bash
python3 scripts/stop_hermes_tmux_agents.py
```

查看全部会话：

```bash
tmux ls
```

查看 Hermes/MCP 状态：

```bash
hermes mcp list
tail -120 ~/.hermes/logs/agent.log
```

限制：

- 每个角色同一时间只处理一个任务，服务内有角色锁；
- 每次投递给 Hermes 的任务都带固定 job ID 和结束标记；
- tmux 启动时会注入 `artifacts/hermes-role-prompts/<role>.md`；每次投递会把完整任务写到 `artifacts/tmux-jobs/<job_id>.job.json`，tmux 里只发送任务文件路径和结束标记，避免直接粘贴长文件内容干扰当前任务解析；
- 超时未返回时，捕获的 tmux 输出会保存到 `artifacts/tmux-jobs/`；
- worker 仍然只允许向 Supervisor 回报，worker-to-worker 消息会被忽略；
- worker 只响应消息开头为 `[任务ID][Supervisor][ASSIGN]` 的派单，不响应 `[DONE]`、`[ERROR]` 或正文里引用的历史 `@`。

## 群里怎么用

```text
/new 你的任务
```

Supervisor 会在群里 @Planner 开始调度。后续 Planner、Researcher、Developer、Tester 都会通过 @Supervisor 回报。

目前支持的群命令：

| 命令 | 说明 |
|------|------|
| `/new <任务>` | 创建新任务，交给 Supervisor 调度 |
| `/status` | 查看当前进行中的任务、处理人、状态、轮次 |
| `/help` | 显示基础用法 |
| `/start` | 显示基础用法 |

手机群聊里会出现短状态卡：

- `[任务ID][Supervisor][STATUS]`：任务创建、派给谁、收到谁回报、是否完成；
- `[任务ID][角色][REPORT]`：worker 完成当前阶段并回报 Supervisor。

工作中状态也由 Supervisor 统一播报；worker 不主动发“我开始处理”状态，避免手机群里出现“不是经理却在对话”的体感。

也可以在群里直接 `@Supervisor` 描述任务。

## 安全说明

- `.env` 包含 Telegram bot token，不能提交或公开；
- `AI_API_KEY` 必须只配置在 `/home/lzy/project/telegrambots/.env`，不要依赖 `~/.hermes/config.yaml` 或其他外部配置；
- `artifacts/` 可能包含用户任务、模型输出、代码草稿和 tmux 调试内容，不要公开同步；
- 服务日志不要打印 bot token、API key 等敏感值；
- 同一套 bot token 只运行一个 polling 服务，避免抢 Telegram update；

- `HERMES_TMUX_YOLO=1` 会跳过 Hermes 安全审批，默认不启用；必须同时设置 `HERMES_TMUX_ALLOW_YOLO=I_UNDERSTAND` 才允许启动；
- 如果 token 泄露，先在 BotFather 或 API provider 侧轮换，再更新 `/home/lzy/project/telegrambots/.env`。

## 故障排查

服务没启动：

```bash
systemctl --user status telegram-ai-team-bot2bot.service --no-pager
journalctl --user -u telegram-ai-team-bot2bot.service -n 80 --no-pager
```

tmux 角色没启动：

```bash
tmux ls
python3 scripts/start_hermes_tmux_agents.py --restart
```

某个角色卡住：

```bash
tmux attach -t telegrambots-developer
python3 scripts/start_hermes_tmux_agents.py --role Developer --restart
```

MCP 工具不可用：

```bash
hermes mcp list
tail -120 ~/.hermes/logs/agent.log
```

常见原因是 systemd 环境的 `PATH` 找不到 `node`、`npx` 或 `codegraph`。当前安装脚本会把安装时的 `PATH` 写入 user service；如果你改了 Node/Conda/CodeGraph 路径，重新运行：

```bash
./scripts/install_systemd_user_service.sh
```

Telegram 没响应：

```bash
journalctl --user -u telegram-ai-team-bot2bot.service -f
```

确认没有另一个进程在轮询同一组 bot token。

重复启动被拒绝：

```bash
cat data/bot2bot.lock
systemctl --user status telegram-ai-team-bot2bot.service --no-pager
```

如果确认旧进程已经不存在，可以删除 stale lock 后重启服务：

```bash
rm -f data/bot2bot.lock
systemctl --user restart telegram-ai-team-bot2bot.service
```

## 当前限制

- 这是实验版，任务短摘要只保存在进程内存中；
- 服务重启后，正在进行的 bot-to-bot 调度不会恢复；
- 如果绕过 `SERVICE_LOCK_FILE` 在其他目录启动同一套 bot token，仍可能互相抢 update；
- 为了省 token，worker 只接收 Supervisor 发来的短交接信息，不读取完整群历史。
- 代码产物默认写到 `artifacts/tasks/<任务ID>/files/`，需要人工或后续执行器确认后再进入项目正式源码。
- `/cancel` 还未实现；
- 每个角色单独选择 Hermes/Claude Code 后端还未实现，目前只是预留设计；
- Hermes tmux 是常驻会话，长时间运行后可能积累上下文；必要时用 `python3 scripts/start_hermes_tmux_agents.py --restart` 重启角色会话。
