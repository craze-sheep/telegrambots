# Task B2B-20260531-000923 审查记录

任务目标：在 `/home/lzy/project/方向研究` 研究世界模型方向，选 20 篇代表性论文，下载论文和代码，逐篇完成 7 问分析，最后形成并排对比表和方向综述。

当前结论：本 task 不应作为有效任务记录保留。它只在 `artifacts/tasks/B2B-20260531-000923` 里生成了模板、派单和一份论文清单，真实工作目录 `/home/lzy/project/方向研究` 没有任何论文、代码、逐篇分析或汇总表。

## 发现的问题

1. Supervisor 派单消息格式错误。
   最新输出出现了重复头部和断裂 username：
   `[B2B-20260531-000923][Supervisor][ASSIGN] @crazysheep_researcher_bo t`。
   这会污染 worker 收到的原始派单，也可能导致 Telegram @mention 失效。

2. Planner 模型调用失败却被包装成成功 REPORT。
   `planner/002-...-report.md` 里显示 `本地 fallback 输出` 和 `模型不可用：RuntimeError`，但服务仍把它写成 Planner 回报并继续调度。

3. 真实工作目录用错。
   用户明确要求产出放入 `/home/lzy/project/方向研究`，但系统只写到了 `artifacts/tasks/.../files/`；真实目录为空。

4. 任务内容被反复输出。
   多个 artifact 和 Telegram 可见消息重复粘贴完整用户需求。用户已明确表示自己知道任务是什么，后续输出应只保留 task_id、短摘要、真实工作目录和下一步。

5. Researcher 产物不可审计。
   报告声称“所有 20 篇论文的 arXiv、作者、年份、会议信息均已逐一验证”，但没有保留网页抓取记录、下载日志或校验证据。清单里还包含 Sora 这类无正式论文/无代码对象，不满足“20 篇顶会论文并拉取论文和代码”的交付要求。

6. 任务未完成但看起来像有进展。
   实际未完成 PDF 下载、仓库 clone、逐篇 7 问分析、并排对比表、科研流程/难点/数据格式总结。只生成清单不能算完成第一批之后的主任务。

7. Handoff 摘要长度和内容控制不一致。
   服务提示要求 300 字以内，但代码之前按 700 字 compact，导致摘要臃肿并夹带长任务内容。

8. 空/失败 task 没有清理机制。
   对于没有真实交付物的失败 task，继续保留 artifacts 会让后续审查误以为任务有有效产出。

## 已做修复

1. 服务端强制规整 Supervisor 可见消息：
   统一生成单个 `[task_id][Supervisor][ASSIGN]` 头部和单个 `@目标bot`，并修复被换行拆开的 username。

2. Worker 模型失败不再伪装成成功 REPORT：
   如果模型调用或出站校验失败，Supervisor 发送 `[ERROR]`，不把 fallback 写成有效 worker report。

3. 支持真实工作目录：
   从用户需求中识别 `/home/lzy/project/方向研究` 这类绝对路径；有真实工作目录时，`FILE:` 产物写入该目录，而不是只写入 artifacts 草稿区。

4. 精简重复任务输出：
   完整需求只保存在 task README；status、派单和角色归档只写 task_id、摘要和真实工作目录。

5. 摘要统一限制为 300 字。

6. Planner 增加 web/fetch 相关能力边界，提示其涉及论文清单和链接时必须验证或标注待验证；Researcher 提示词增加证据留存要求。

7. 对没有真实交付物的失败 task 增加清理逻辑。

## 后续建议

重新发起这类科研任务时，应先让具备 web/fetch 能力的角色产出带证据的论文清单，再让具备 terminal/code_execution 能力的角色把 PDF 和代码实际下载到 `/home/lzy/project/方向研究`，最后分批做逐篇分析和总表。
